Real customer data is confidential, regulated, and unavailable for open projects. How Churn Labels Were Created

Churn probability was generated via a logistic formula — the same math used in logistic regression — with domain-realistic weights:

logit = -1.25
  - (sentiment_score-50) × 0.04   # low sentiment → churn
  + escalated_support × 1.8       # escalation is strong signal
  + complaint_count × 0.35
  - feature_adoption × 1.2        # engaged users stay
  + (contract=='monthly') × 0.6   # short contracts → churn
  - auto_renewal × 0.5
  + payment_failures × 0.4
  + noise                         # random variation

p_churn = 1 / (1 + e^(-logit))
Intercept of -1.25 was tuned iteratively to produce a 13.4% churn rate — matching realistic SaaS industry averages.

What is Feature Engineering?

Raw data rarely tells the full story. Feature engineering transforms raw columns into signals the model can use more effectively. It combines domain knowledge with statistical insight — creating new variables that capture patterns the model wouldn't discover on its own from raw inputs.

No ML model was used in feature engineering. Every feature was crafted using domain logic and statistical rules — human knowledge converted into code.

Model 1 — Logistic Regression WINNER

Learns a weighted sum of all 61 features and passes it through a sigmoid to produce a churn probability. Simple, fast, interpretable.

How it works

z = w1×sentiment + w2×churn_risk + ...
p = 1 / (1 + e^(-z))

Key settings

  • L1 regularisation — drives useless feature weights to exactly zero (automatic feature selection)
  • C = 0.01 — strong regularisation; model is forced to focus on only the clearest signals
  • class_weight='balanced' — upweights the rare 13.4% churners in training
  • GridSearchCV — tried 10 combinations × 5 folds = 50 training runs
AUC-ROC: 0.8386

Model 2 — XGBoost (Structured)

Gradient boosted trees trained on 42 non-sentiment features. Builds 200 trees sequentially — each one correcting the errors of the previous.

How boosting works

  • Tree 1: makes first predictions for all customers
  • Tree 2: trained on residuals (errors) of Tree 1
  • Tree 3: fixes remaining errors after Tree 1+2
  • …repeat 200 times with learning_rate=0.1

Key settings

  • max_depth=3 — shallow trees prevent overfitting
  • scale_pos_weight=6.46 — accounts for 6.46:1 class imbalance
  • subsample=0.8 — each tree sees random 80% of customers
AUC-ROC: 0.7905

Model 3 — XGBoost (Sentiment)

Same algorithm as Model 2 but trained exclusively on 19 sentiment and support features. Rationale: sentiment data is fundamentally different from behavioural data — a specialist model might capture it better.

AUC-ROC: 0.7987
Sentiment features alone slightly outperform structured features alone — confirming sentiment is the strongest churn signal in this dataset.

Model 4 — Ensemble Stack

Meta Logistic Regression trained on out-of-fold predictions from Models 2 and 3. Learns which model to trust more in each situation.

Out-of-Fold (OOF) predictions

  • Split training into 5 folds
  • For each fold: train XGB on 4 folds, predict on 1
  • Every customer gets a prediction from a model that never saw them
  • Meta-LR trained on these honest predictions
AUC-ROC: 0.8184

Why Threshold Matters

Every model outputs a churn probability (0–1). To make a yes/no intervention decision, you need a threshold: everyone above it gets contacted. The default of 0.5 is almost never optimal — especially with class imbalance or asymmetric costs.

Key Insight: Why Low Precision (29%) is Acceptable

Precision of 29% means only 1 in 3.4 customers contacted is a true churner. This sounds bad — but the economics justify it:

Each churner saved:       +$5,000
Each false alarm:          -$500

Break-even: save 1 churner per 10 contacts = $5,000 vs $5,000
At 29% precision:  save 1 churner per 3.4 contacts = $5,000 vs $1,700

Net gain per churner caught: $5,000 - $1,700 = $3,300 profit
At cost-optimal threshold: contact broadly, accept false alarms — the math strongly favours it.

Step 7

A/B Test Design & Simulation

Why Run an A/B Test?

The model identifies who might churn. But does the intervention actually stop them? Without a control group, you can't separate the intervention's effect from natural retention. The A/B test is how you prove causation — not just correlation.

Control group: High-risk customers flagged by model but NOT contacted. They churn at the natural baseline rate.
Treatment group: High-risk customers who DO receive the intervention. Their churn rate should be lower if it works.

The A/B test happens BEFORE full rollout — it's the pilot. Only after it proves the intervention works do you invest in contacting all at-risk customers.

Empirical (99.9%) vs Theoretical (80%) Power — Why Different?

Theoretical 80% was calculated for detecting the MDE (2% absolute reduction) — the smallest effect we care about.

Empirical 99.9% was measured from simulations using the actual treatment effect (3.37% absolute = 25% relative) — which is 68% larger than the MDE.

Designed for:  2.00% abs reduction → 80% power
Actual effect: 3.37% abs reduction → 99.8% power

Like studying for a hard exam (2% MDE)
and getting an easy one (3.37% effect).
You were over-prepared.
Key concept: We designed the sample size for the worst acceptable case (MDE). The simulation runs with the expected case (true treatment effect). At n=4,283, detecting a 3.37% absolute reduction is near-certain.

Key Statistical Concepts

Z-score & Significance

The z-score measures how many standard deviations the observed difference is from zero (what we'd expect under the null hypothesis of no effect). At z = 4.83, the result is 4.83 standard deviations away — a 0.0001% chance of occurring by luck.

z = (ctrl_rate - trt_rate) / SE
  = (13.47% - 10.10%) / 0.70%
  = 4.83   >>  1.96 threshold

Anything above z = 1.96 is significant at α = 0.05 (two-tailed). 1.96 is the fixed z-score where only 5% of random noise falls outside ±1.96.

MDE — Minimum Detectable Effect

The smallest improvement that would matter to the business. Set at 2% because smaller reductions don't justify the $500/customer outreach cost.

MDE = 2%   → n = 4,283 per group
MDE = 1%   → n = 17,000 per group
MDE = 0.5% → n = 67,000 per group

Smaller MDE = harder to detect = needs more data. Choosing MDE is the most important A/B test design decision.

Audit

Pitfalls Found & Fixed

1. Data Leakage in Scaling

Problem: StandardScaler was fit on all 50,000 rows in feature_engineering.py — including test data. The scaler "saw" test data statistics before training.

Fix: In train_models.py, scaler is fit only on X_train, then transform() applied to val and test separately.

Impact: inflated validation scores that don't reflect real-world performance.

2. The Accuracy Trap

Problem: With 86.6% non-churners, a model predicting "never churn" achieves 86.6% accuracy — but is completely useless.

Fix: Use AUC-ROC, AUC-PR, F1, and business metrics (net value) instead of accuracy. These expose the dumb baseline for what it is: AUC = 0.50.

Always compare to a meaningful baseline, not just raw accuracy.

3. Wrong ROI Calculation

Problem: Initial financial model compared the one-time intervention cost against year-1 revenue only — showing a false negative ROI of -66%.

Fix: ROI must use LTV (5-year value) since the intervention cost is paid once but the retained customer generates revenue for 5 years.

Correct ROI: +68.4% on LTV basis.

4. Class Imbalance

Problem: 86.6% non-churners vs 13.4% churners. Models learn to mostly predict "no churn" because it's the easy path to low loss.

Fix: LR uses class_weight='balanced'; XGBoost uses scale_pos_weight=6.46 (ratio of majority to minority class).

Without this fix, recall collapses to near zero — the model misses almost every churner.

5. Default Threshold of 0.5

Problem: Using 0.5 as the churn threshold ignores the asymmetric cost structure. A missed churner ($5,000 loss) is 10× worse than a false alarm ($500 cost).

Fix: Cost-optimal threshold of 0.409 maximises net value at $3.1M — 29% higher than F1-optimal at 0.701.

Always select threshold based on business costs, not statistical symmetry.

6. Empirical vs Theoretical Power Confusion

Problem: Theoretical power (80%) and empirical power (99.9%) appear contradictory — which one is right?

Fix: They measure different things. 80% is power at the MDE (2% effect); 99.9% is power at the actual treatment effect (3.37%). Both are correct for their respective effect sizes.

Always specify which effect size power is being calculated for.

7. Feature Splitting Hypothesis (Not Validated)

Problem: We split XGBoost into structured + sentiment models assuming specialisation would help. It didn't — the ensemble scored lower than LR.

Fix: Tested XGBoost on all 61 features. Still lost to LR. Lesson: validate hypotheses with experiments, don't assume architectural choices are beneficial.

Intuitive design choices need empirical validation.

8. Confusing A/B Simulation with Real Test

Problem: The 1,000 simulations might be mistaken for 1,000 actual experiments on real customers.

Fix: Be explicit — simulations use synthetic binomial draws to stress-test the test design. The real A/B test (Phase 1–2) runs on actual customers in production.

Simulation = planning. Real A/B test = evidence. They are sequential, not the same.

9. Collinear Features Left In

Problem: Some engineered features were near-perfect linear combinations of others (r > 0.95), adding no new information while inflating dimensionality.

Fix: 9 collinear features dropped: monthly_spend_current, sentiment_score_sq, new_customer_flag, and 6 others.

Collinear features destabilise coefficients and waste model capacity.

10. np.trapz Removed in New NumPy

Problem: AUC calculation used np.trapz() which was deprecated and removed in NumPy 2.0.

Fix: Replaced with np.trapezoid() which is the current API.

Always pin dependency versions or test against latest before deploying.

Top 5 Learnings

  1. Feature engineering > model complexity. A logistic regression on well-engineered features beat XGBoost across every metric. Invest in features before chasing algorithms.
  2. Always use business metrics, not just AUC. Two models with similar AUC can have very different net values depending on where their errors fall.
  3. Threshold is a business decision, not a statistical one. The cost-optimal threshold (0.409) generated $700K more than the F1-optimal one (0.701) by accepting low precision.
  4. Power analysis before the experiment. Running an A/B test without knowing if you have enough data is expensive. n=4,283 was calculated upfront to guarantee 80% power.
  5. Phased deployment reduces risk. Committing $3.4M without a canary phase is reckless. The 3-phase rollout lets you validate at each stage before full investment.
