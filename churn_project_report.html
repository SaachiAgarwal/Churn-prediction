BACKGROUND

What is Churn — and Why Does it Matter?

Churn means a customer stops using your product and cancels their subscription. In simple terms: they leave.


For a subscription business like Adobe (which this project is modelled on), losing a customer means losing all future revenue from them. It is almost always 5–10× cheaper to keep an existing customer than to acquire a new one — so even a 1% reduction in churn rate can be worth millions of dollars.


The goal of this project is to predict which customers are about to churn — before they do — so retention teams can intervene with offers, support, or outreach.

STEP 1

Synthetic Data Generation

Why synthetic data?

Real customer churn data is confidential and hard to share publicly. Instead, we generated a realistic dataset using statistical distributions — the kind of patterns that would actually appear in a real subscription business. This lets us practice the full pipeline without needing proprietary data.

How was it built?

Each feature was generated independently using an appropriate probability distribution:


Feature TypeDistribution UsedWhy that distribution?
AgeNormal (bell curve)Age is naturally centred around a mean with spread on both sides
Tenure monthsExponentialMost customers are relatively new; a few are very long-term
Complaint countPoissonCount data — most customers have 0 complaints, few have many
Feature adoption rateBeta (0–1)A proportion that skews toward lower adoption for most users
Monthly spendExponential + offsetMost customers spend modestly; a few are very high spenders
Region, Product, ContractWeighted random choiceReflects realistic business proportions (e.g. 70% annual contracts)

How was churn generated?

Churn wasn't assigned randomly — it was calculated using a logistic formula that mirrors how churn actually works in the real world. Each risk factor contributed a weight to a "churn score", which was then converted to a probability:

churn probability = sigmoid(
    intercept                          # sets the baseline ~13.5% rate
  - (sentiment_score - 50) × 0.04    # high sentiment → lower churn
  + (spend_trend == declining) × 1.2  # declining spend → higher churn
  - num_products × 0.18               # more products → harder to leave
  - (tenure / 120) × 1.0             # longer tenure → more loyal
  + escalated_support × 1.8           # escalation → much higher churn
  + complaint_count × 0.35            # complaints → higher churn
  + noise                             # real-world randomness
)

This ensures correlations are realistic and testable — for example, escalated customers churn at 39% vs 8.8% for non-escalated customers.

We defined a customer as "at-risk" if ANY of these 4 conditions are true:

    OR spend_trend == -1           # declining spend
)

Feature Engineering Pipeline

What is feature engineering?

Raw data columns are rarely in the best shape for an ML model. Feature engineering is the process of transforming, combining, and creating new columns that make patterns easier for a model to detect.


Think of it as translating business knowledge into maths. Instead of giving a model raw numbers, you pre-compute the signals you already know matter — so the model can focus on combining them rather than discovering them from scratch.

💡 Why composite features beat individual ones No single feature perfectly predicts churn — but combining 7 weak signals into one weighted score creates a stronger predictor. The model can then use this summary alongside the individual signals, using whichever is most useful. This is also why the composite features ranked #1 and #10 out of all 61 features.

Scaling — StandardScaler

Before the collinearity check, all continuous features were scaled using StandardScaler:

scaled_value = (original_value - mean) / standard_deviation

This transforms every continuous feature to have mean = 0 and std = 1. Without this, a feature like monthly_spend_avg (range: $10–$2,000) would overpower feature_adoption_rate (range: 0–1) simply because its numbers are bigger — even if adoption rate is more predictive.


Binary flags (0/1) were left unscaled as they're already on a consistent scale.

Collinearity Drop — 9 Features Removed

Two features are "collinear" when they carry nearly identical information (correlation > 0.95). Keeping both confuses the model — it's like giving it the same clue twice.

AUDIT

Pitfalls & Things We Should Watch Out For

Every data science project has assumptions and shortcuts that can cause problems downstream. Here is an honest audit of this project's weak points.

🚨 Pitfall 1 — The data is synthetic (not real)

All 50,000 customers were generated by a formula. Real churn data is far messier — customers churn for reasons that aren't in any dataset (competitor pricing, life events, budget cuts). Correlations in synthetic data are cleaner and more predictable than in the wild.

✅ Fix: Use synthetic data only for practice and pipeline development. Validate every insight on real customer data before acting on it.

🚨 Pitfall 2 — Churn labels were generated from the same features we're using to predict churn

We generated churn using sentiment, spend_trend, etc., and then also use those features to predict churn. In a real project this is fine — but here it means our model is essentially reverse-engineering a formula it was designed against. Real-world performance will be lower because real churn has many unmeasured causes.

✅ Fix: Accept this as a limitation of synthetic data. Any model trained here will appear "too good" — treat reported metrics with appropriate scepticism.

🚨 Pitfall 3 — No train/test split has been done yet

All analysis and feature engineering was done on the full 50,000 rows. When we eventually train a model, we must split the data first — otherwise the model has "seen" all the data during training and test metrics will be inflated (overfitting).

✅ Fix: Before any model training, split: 70% train / 15% validation / 15% test. Feature engineering should be fitted on train and only applied (not refitted) to val/test.

🚨 Pitfall 4 — StandardScaler was fit on the full dataset

We scaled all 50,000 rows together. In a real ML pipeline, the scaler must be fitted only on training data and then applied to validation and test data. Fitting on all data leaks information from test rows into the training process (data leakage).

✅ Fix: Move scaler.fit_transform() inside the train split only. Use scaler.transform() (not fit_transform) on val/test sets.

🚨 Pitfall 5 — engagement_score was computed from raw features that are also in the model

engagement_score is derived from login_frequency_30d, feature_adoption_rate, and days_since_last_login — all of which are also individual features in the dataset. The model now has access to both the components AND the composite. This is mild redundancy but not a critical issue since we kept individual features as well.

✅ Fix: Either drop the raw component features if using the composite, or keep both and let the model decide which is more useful. We kept both — which is fine for tree-based models.

🚨 Pitfall 6 — product_diversity and num_products are highly correlated (r = 0.82)

These two features measure almost the same thing — how many products a customer uses. The collinearity check threshold was 0.95, so both survived. But r = 0.82 is still high enough to cause mild issues in linear models (multicollinearity).

✅ Fix: For linear/logistic regression, drop one. For tree-based models (XGBoost, Random Forest) this is less of a concern as they handle redundant features better.

🚨 Pitfall 7 — Composite feature weights were set manually, not learned from data

The weights in churn_risk_score (e.g. escalation_flag × 0.25) were chosen based on correlation values we observed. This is reasonable but imprecise — a model trained on data will find better weights automatically.

✅ Fix: Treat the composite features as useful starting points for EDA and rule-based targeting. Let the ML model learn its own weighting during training — don't force the hand-tuned composite on it.

🚨 Pitfall 8 — payment_method_changes is a proxy, not the real thing

The raw data didn't include a "payment method changes" column, so we used product_changes_6m as a proxy. These are not the same thing. The feature has near-zero correlation with churn (r ≈ 0) and is essentially noise.

✅ Fix: Drop payment_method_changes from the final feature set — it adds no signal and is misleadingly named. A real dataset would have actual payment method change events.

🚨 Pitfall 9 — Class imbalance not yet handled

13.4% churn means the dataset has roughly 6.5 retained customers for every churner. Most ML models will naturally learn to predict "no churn" more often. We haven't applied any resampling (SMOTE, oversampling, undersampling) or class weights yet.

✅ Fix: When training a model, use class_weight='balanced' (sklearn) or scale_pos_weight (XGBoost), or apply SMOTE on the training set only. Evaluate with F1, AUC-ROC, and precision-recall — not accuracy.

🚨 Pitfall 10 — Correlation ≠ Causation

We found that escalated_support correlates strongly with churn (r = 0.32). But this doesn't mean escalations cause churn — it's more likely that underlying dissatisfaction causes both escalations and churn. Acting on this by suppressing escalations (e.g. making it harder to reach support) could make churn worse.

✅ Fix: Use correlations to identify where to look, not to prescribe actions. The business interpretation must come from domain experts, not statistics alone.
NEXT

What Comes Next — The Road to a Model

🔜 Step 5 — Model Training

  • Split data: 70/15/15 train/val/test
  • Baseline: Logistic Regression
  • Primary: XGBoost or LightGBM
  • Tune with cross-validation
  • Evaluate with AUC-ROC, F1, Precision-Recall curve

🔜 Step 6 — Model Evaluation

  • Confusion matrix at multiple thresholds
  • Precision-recall tradeoff (business cost of false positives vs missed churners)
  • Decile lift analysis
  • SHAP values for explainability

🔜 Step 7 — Business Output

  • Score each customer 0–100% churn probability
  • Prioritise top-risk customers for retention team
  • Estimate ROI: cost of intervention vs revenue saved
  • Set up monthly scoring pipeline

🔜 Step 8 — Monitoring

  • Track feature drift over time (do distributions change?)
  • Monitor model performance as new data arrives
  • Retrain quarterly or when AUC drops below threshold
  • A/B test retention interventions
